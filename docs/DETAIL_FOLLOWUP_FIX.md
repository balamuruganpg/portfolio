# Detailed follow-up and Groq verification

## Observed problem

The configured API was calling Groq, but the interface did not show the actual provider on each reply. A vague follow-up such as “I said more details” lost the project-specific retrieval terms. The default short-answer instruction and near-duplicate overview sections produced repetitive answers. Groq's alternate citation syntax could also reject otherwise useful drafts.

## Changes

- Resolve vague detail requests from conversation history. Retrieve diverse implementation, workflow, interface, output and limitation sections; prefer sections not already cited and deduplicate equivalent GitHub/PyPI text.
- Request detailed explanations when asked, without imposing that length on ordinary answers.
- Request strict structured paragraphs from supported Groq models. Each paragraph supplies its source IDs; the application renders citations only after checking their bounds and source claims.
- Allow one validation rewrite within a shared 16-second deadline, including expansion when a detail answer is too short despite substantial supplementary evidence. Independently valid sentences can be retained with their original paragraph source IDs, followed by full-answer validation. Protected RAI-Axiom and CertiRoute result narratives remain indivisible.
- Strengthen checks against treating CLI example values as defaults, inventing exclusive format support, or converting “optimized for English” into “English-only.” Match academic rank as a word rather than rejecting algorithmic “ranking.”
- Allow a rate-limited Groq model to try the secondary Groq model. Invalid credentials still block the provider. Show the actual provider/model per reply, including whether validation required a guarded fallback.

## Verification

`npm run test:assistant` covers structured source IDs, citation normalization, bounded repair, factual rejection, retained verified material, provider fallback and request cancellation. `npm run test:rag` covers diverse detail retrieval, vague follow-ups, fresh sections and duplicate-source removal.

`npm run test:details` uses the live local chat endpoint with the exact sequence “Tell me more about VeraScan” followed by “I said more details.” It requires both responses to be generated by Groq, contain at least 120 words, cite at least two implementation sections, and use additional evidence in the second answer. This is an integration check against a nondeterministic external API and requires a valid key and available quota.

Existing factual guardrails, source snapshots, protected project metrics, request validation, rate limits and secret handling remain in place. Passing these checks does not establish that every possible model response is correct; visitors can inspect the cited source sections.
